# Spec: adaptive pocket clearing

**Removed 2026-10-13** (docs/decisions/0017-scope.md): the code is at the local tag
`adaptive-final`; projects that use it load and are refused when generating. Kept as
history.

Status: **approved 2026-10-10** (Q1–Q5 as recommended). Implemented; refinements found while
building it are marked *Implemented:*. Superseded in part by docs/specs/adaptive-fronts.md:
since schema 13 the strategy has no `load`; adaptive cuts the pocket's stepover (§2 below is
the v7–v12 format).

User request (2026-10-10): adaptive clearing, after trochoidal.

## 1. What it is

Adaptive clearing steers the tool so it always cuts about the same amount: the **engagement**
(how much of the tool's circumference is in uncut material) stays near a target all along
the path, including corners, where ring pockets suddenly cut with the full tool. The path is
a free curve that follows the uncut material, not offset rings. It allows deep step-downs at
high feed, like trochoidal, but without the time trochoidal loops spend in air.

It's the most complex strategy so far. This spec keeps it **verifiable**: the path is
generated by simulation, but every move is checked against the walls exactly as other
pockets are, and what it leaves is found by the existing uncut-material check.

## 2. Format (no version bump)

A third pocket strategy:

```json
"strategy": {"type": "adaptive", "load": 0.1}
```

- `load`: the target engagement as a fraction of the tool diameter, the sideways cut width a
  straight pass would take (0 < load ≤ 0.5). The GUI fills 0.1 when switched on.
- Optional field, as the strategy already is: no version bump.

## 3. How the path is made

r = tool radius, D = diameter, w = load × D.

1. **Material model**: the pocket as a grid of square cells (side h = min(D / 30, 0.2 mm)),
   each uncut or cut. Only cells the tool can reach (within r of the pocket shrunk by r) count.

   *Implemented:* the model cuts with r − h/√2, so a cell is marked cut only when all of it
   is within the tool. Marking cells cut by their centres left specks a cell wide that the
   model thought done (found by the property test). Counting and clearing use the same
   radius, so the model never follows material it can't clear.
2. **Start**: plunge at the point of the pocket furthest from the walls, and cut a small
   circle there (radius w) to open a start.
3. **Steering**: from the current point, advance in steps of about h. At each step, choose the
   direction (by bisection over the angle, turning towards the uncut side) whose engagement
   (the share of the tool's front arc over uncut cells) is closest to the target engagement
   for `w`. Mark the cells the tool sweeps as cut.
4. **Constraint**: the tool centre must stay in the pocket shrunk by r (checked each step
   against the walls with the same distance index the verification uses). A step that would
   leave it is turned along the wall instead.
5. **Next pass**: when engagement can't be kept (the material near the path is gone), the
   tool goes to the nearest uncut boundary.

   *Implemented:* first, without lifting, the tool **seeks**: it moves through what is
   cleared (inside the allowed area, along walls) towards the uncut material within
   5 × r, and follows again once it cuts. Only when nothing is within that reach (or the
   way is blocked) does the pass end. Ending passes on a few low-cut steps instead broke a
   100 × 60 mm pocket into 918 passes (each a retract and plunge); with seeking it is 11.
   When a pass does end, the tool goes to the nearest uncut boundary: feeding at depth if that's short and safe (the
   `keep_tool_down` rule), otherwise retract, rapid, plunge into cleared material.
6. **End**: when no reachable uncut cell is left. Then the ordinary **wall pass** (the ring
   pocket's last ring) at each depth finishes the walls and islands.

   *Implemented:* the passes leave a band one load wide along the walls to the wall pass,
   so it cuts about one load, not a full-width chunk. The plunge point is in the deepest part
   of the pocket (its last non-empty shrink, r at a time).
7. **Smoothing**: the steps are simplified (dropping points while the path stays within
   `ARC_APPROX_TOL_MM`), so the program isn't one line per 0.2 mm.

Each depth pass repeats the same path (computed once for the pocket's outline), as ring
pockets do today.

## 4. What's guaranteed and what isn't

Guaranteed (checked, an error or warning otherwise):
- No gouge: every move keeps r (minus clearance) from walls and islands; verified like rings.
- Nothing silently left: the uncut-material check runs on the real path; leftovers warn.
- The independent checker passes; deterministic output (no randomness, fixed order).

Best effort (a quality, not a safety property): the engagement stays near the target. Tests
measure it (§8) but a few spikes, e.g. where passes meet, are possible.

## 5. Arcs, entry, links

- Output is G1 (the path is a free curve). Fitting arcs to it could come later.
- Plunge is straight down, so a centre-cutting endmill is required (as for other pockets).
  Helical entry is its own later step.
- Links follow `keep_tool_down` as for the other strategies.

## 6. Performance

A 200 × 150 mm pocket with a 6 mm tool is about 750 × 560 = 420 000 cells, and a path of a
few 10 000 steps, each testing a few directions over a few hundred cells: well under a
second in a release build. Planning runs on every *Generate*, so this matters; tests include
a timing guard on a large pocket.

## 7. Out of scope

Rest machining with a smaller tool, helical/ramp entry, arc fitting, engagement-based feed
adjustment, adaptive profiles.

## 8. Tests

- Square, L-shaped and island pockets: no gouge, no uncut warning, wall pass last at each
  depth, deterministic (same input twice, same moves).
- Engagement: sampled along the path (from the material model), the median within 20 % of
  the target, and over 90 % of samples within 50 %. *Implemented:* sampled on the cutting
  steps; seeking moves through cleared material aren't cutting. Measured: square 97.9 %,
  L-shape 96.3 %, pocket with an island 96.8 % within 50 %; median 1.0 in all three.
- *Implemented:* timing: the 200 × 150 mm pocket plans in 1.35 s (release), 4.5 s (debug).
- A pocket too small for the start circle falls back to the wall pass with a note.
- Property: random pockets with islands: no gouge, no uncut warning.
- Rings and trochoidal: every existing golden file unchanged.
- New golden file: the drawn_part pocket cleared adaptively; passes the checker.
- Timing: the 200 × 150 mm pocket plans in under 2 s (release) / a looser bound in debug.

## 9. Decisions (approved 2026-10-10)

1. **Approach** (§3): Chipload's own grid-based simulation, no new dependency. (User,
   2026-10-10: we never copy someone else's code; this is designed and written here.) The
   alternative is porting FreeCAD's adaptive clearing (C++, LGPL-2.1+, about 3 000 lines on
   top of the Clipper library): proven, but a large port of foreign code that we'd then have
   to verify anyway. **Our own**, kept simple and verified like the rest.
2. **Setting** (§2): `load` as a fraction of D, default 0.1. **Yes.**
3. **Engagement is best effort** (§4), safety is guaranteed by verification as everywhere
   else. **Yes.**
4. **G1 output** with path simplification; arcs, helical entry later (§5).
   **Yes.**
5. **Staging**: this is a larger piece of work than trochoidal. I'd build it behind the
   strategy setting and ship it once the tests in §8 pass, possibly over several commits.
   **Yes.**
